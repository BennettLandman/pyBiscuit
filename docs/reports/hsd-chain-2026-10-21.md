## New finding: the oracle could not run `--icomesh` at all

`HSD.cpp:316` (`const float *p = V.unit().fv();` in the `--icomesh` branch of `init`) reads the stack slot of a destroyed temporary
(`MathVector::unit()` returns by value, `fv()` points into it). With Apple clang -O2 every icomesh sample is garbage and the run dies ("no closest
triangle found at [3.3e26, ...]"). The previous `hsd-nofma` build can therefore not run any of BISCUIT's four calls. The goldens come from
`hsd-icomesh-nofma` (`HSD_PATCH_ICOMESH=1 scripts/oracles/build_hsd_nofma.sh`, a one-line sed copy of `HSD.cpp`, otherwise identical, outputs to a new
directory so the existing oracle is untouched). The port computes the intended value. The same pattern at `HSD.cpp:2638` (guess) and other
`.unit().fv()` sites survives in clang's layout; the image's gcc build is assumed to keep the value at 316 (otherwise production would fail), which the first
Linux run confirms for free (Q1).

## How to read the comparisons: the oracle is chaotic

BISCUIT's chain is a sequence of line searches with step doubling/halving, flip tests and a damped Newton solve. A one-float32-ulp change of **one input value**
(of 2,562) changes the oracle itself, e.g. fixture `lh` call 2 (GD level 4): 38-45 iterations, final energy +-1 %, coefficients up to 0.04; `rh` (lhorder) call 4:
57-66 iterations, final energy +0.4 %, coefficients up to 0.014. Whole chains (call 1 input changed by one ulp): `lh` final sphere median 0.19-6.5 degrees, `rh`
0 to 0.12 degrees. At template scale (below) the final sphere differs by 0.47, 2.05 and 5.9 degrees median between three one-ulp-different oracle chains.
(This is the same situation as LGI at cortex scale, Q14.)

So the policy bounds (`validation-tolerances.md`: sphere median <= 0.01 degrees, p99 <= 0.1 degrees, energy 0.1 %, coefficients 1e-4) cannot be met by **any**
implementation, including a second run of the oracle, for several calls. The goldens therefore store the oracle's own response to ulp-level input changes
(6 members per call: alternating "one value +-1 ulp" and "every value 0 or +-1 ulp", plus 6 whole chains), and `test_each_call_vs_oracle` /
`test_chain_end_to_end_vs_oracle` accept `max(policy, 1.5 x oracle spread)`: a stable call is held to the policy, a chaotic call to what the oracle itself shows.
No bound in `validation-tolerances.md` was changed. Whether to adopt this "oracle-spread" rule is an owner decision (below).

State-level agreement (same coefficient file, same inputs): energy to 1e-10 relative at degree 0 and degree 10, damped gradient direction to 1e-7 relative
(`state_level_check` in the metrics file; throwaway script, not kept as a test because it needs the shipped template). The trajectories diverge because of
chaos, not because of a larger state-level error than at fixture scale.

End to end (port's own coefficient files, 4 calls): **the port aborted** with `Fatal error: Property - no closest triangle found in subject 1` in call 4 (phase 3), so there is no end-to-end sphere comparison at template scale.
The oracle's own one-ulp chains end 0.47, 2.05 and 5.9 degrees (median) from the baseline oracle chain, so an end-to-end agreement bound is meaningless here anyway.
The abort is not a port-specific error:

* From the port's call-3 file the port ends in that abort in 3 of 5 one-ulp variants (2 complete, 72 and 55 iterations); from the *oracle's* call-3 file it completes 5 of 5 (25-29 iterations);
  the oracle from the port's call-3 file completes 5 of 5 (42-60 iterations, energy 3.49-3.52). Small samples: the observed difference is 3/5 against 0 of about 15 oracle runs of call 4 or of whole chains, suggestive, not shown to be systematic.
* On the dumped port mesh at the abort, the unmodified MeshLib `AABB_Sphere::closestFace` (oracle harness) also returns -1 for the one failing sample (of 163,842).
  The sample lies about 2e-7 from an edge; the float32 `cart2bary` of the two adjacent faces is below -1e-5 for both (float64 gives +2.6e-5 for one of them).
  Upstream accepts only coefficients >= -1e-5 and then retries with larger boxes that skip already-visited faces, so it exits there too.
  This is a **latent upstream fragility at ico7**: a subject whose trajectory leaves a sample in that float32 gray zone aborts BISCUIT's call 4. The port does not
  add a fallback (AGENTS.md: preserve stopping rules). A proposal (e.g. a float64 re-check before giving up) needs owner approval.
